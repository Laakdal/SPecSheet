==========================================================================
(a) Two dots on the floor in front of the bumper
==========================================================================
Anchors with the lowest y (truck space: x right, y up, -z forward):
     x       y       z     slot        selection
   0.000   0.084  -2.830   f_mudflap   (empty)
   0.000   0.214   2.814   r_mudflap   scania_v8...r_mudflap
   1.240   0.231   0.541   exhaust_r   (empty)            <- right side, hidden by the far-side rule
   0.000   0.243  -3.179   b_grill     (empty, "Bull Bar: None" in the sidebar)

Confirmed: f_mudflap and b_grill are EMPTY in the Scania S preset. For empty slots assembly::anchors()
uses the mean of the slot's locators. Chassis chs_4x2.pmd locators:
   b_grill    pos (0.000, 0.243, -3.179)
   f_mudflap  pos (0.000, 0.084, -2.830)
These are attachment pivots, not where the part appears:
   hss_bottomgrill_01.pmd (b_grill)  local AABB y 0.000..0.115, z +0.066..+0.844
      -> world part spans z -3.11..-2.34, i.e. it sits BEHIND the locator; the locator is the part's front-bottom corner.
   kotr_p.pmd (f_mudflap)            local AABB x -1.094..+1.094, y 0.089..0.258
      -> one centred locator carries a LEFT+RIGHT pair; x = 0 is under the truck between the wheels.
Hypothesis (strong): the two floating dots in 01/05 are b_grill and f_mudflap: both x = 0, the only two front anchors below
y = 0.25, matching the dots' position below the front bumper on the centreline.
Contributing (Confirmed from RENDERING.md, D7): occlusion is approximate; DOM markers have no depth test, so an anchor under
or inside the truck still draws.

Fix: an empty slot's anchor should be where a part WOULD appear: place the slot's first compatible option (fallback / default
/ first) at its locators, take that model's world AABB, then apply the existing rules (centre; move to the -x face when
inside the cabin; interior test). Fall back to the raw locator only when no option has a model. In Bevy, depth-test markers
against the scene (raycast against mesh AABBs, or read back depth) instead of the far-side half-space heuristic.

==========================================================================
(c) Under the Bridge camera crops the truck
==========================================================================
Confirmed (def/desktop/config.under_bridge.sii):
   camera_position (0.0, 3.1, -15)   camera_aim (0.0, 2.5, -0.7)   camera_fov 20   truck_rot (0, 15, 0)
Confirmed (crates/specsheet-data/src/scene.rs, test camera_must_stand_outside_and_look_through_the_truck): the app picks this static
pose for the bridge, keeps FOV 20 and only moves the orbit target onto the same view ray. The app reproduces the data as
written, using FOV as the vertical angle (three.js PerspectiveCamera).
Geometry: 15 m away with a vertical FOV of 20 deg gives ~4.0 m visible height at the cab front (z ~ -3.7). With the aim at
y ~ 2.5 the frame covers y ~ 0.5..4.5, so the bumper/wheels are cut: the crop in 06.
Hypothesis: the /def/desktop scenes are the game's hub ("desktop") BACKGROUNDS, not dedicated tuning-screen scenes.
Evidence: directory name; steam_inventory_id per scene; icon_path; locale keys "desktop" ("Back to desktop") and
"select_background". The static pose is framed for the full-screen 16:9 hub with its own UI, and the cinematic cameras are
`orbit_camera` units with FOV 30/45/60. Whether the configurator reuses these poses is Unknown.
Unknown: whether SCS camera_fov is vertical or horizontal (if horizontal, the game frame is even tighter).

Fix: keep the scene's view DIRECTION (position -> aim) and FOV, but set the distance so the assembled truck's world AABB fits
the actual viewport (the viewport is narrower than the hub because of the sidebar), with a margin. Re-check against an
in-game screenshot of the same scene. Relabel F7 in docs from "tuning scene" to "desktop background scene (also used as the
configurator backdrop: Hypothesis)".

==========================================================================
(d) Garage looks white and flat
==========================================================================
Confirmed (def/desktop/config.sii, "Home at Last"): light_direction (0,-8,0) straight down; light_diffuse (3,3,3) white;
light_ambient (0.3,0.3,0.3); fog_color (0.9,0.9,0.9) density 0.0018; light_environment 1.2. The scene is meant to be
bright, neutral and white, so "white" is faithful.
Confirmed (desktop_garage.pmd, 31 materials): the parts in part_order (a, b, reflection) are almost all
`eut2.dif.spec.mult.dif.spec[.add.env][.tsnmap|.tsnmapuv].rfx`. Example automat/cc/cc9de879db5d57dd.mat:
   texture_base       /material/tiled/metal_plates_gs_01.tobj            (tiled, greyscale)
   texture_mult       /model/ui/garage/ao_textures/metal_plates_v3.tobj  (baked ambient occlusion, clamp)
   texture_nmap       /material/tiled/metal_plates_gs_01_nrm.tobj
   texture_reflection /material/environment/showroom_cube/reflection.tobj (the game's own cube map)
Confirmed (docs/RENDERING.md): the app uses only texture_base and ignores normal and reflection maps, and replaces
reflections with RoomEnvironment.
Root cause: the baked AO (texture_mult) carries the garage's shading: corners, shadows under objects, depth. Without it the
tiled greyscale base renders uniformly lit, which looks flat. Missing normal maps and the showroom cube reflection add to it.
Hypothesis: texture_mult uses the second UV set (separate, non-tiled UVs typical of baked AO); check the PMG UV channel count
per piece before relying on it.

Fix, in order: (1) multiply texture_mult (AO) onto base: biggest gain, cheap; (2) load the material's texture_reflection cube
(showroom_cube) as the environment map instead of a generic one; (3) normal maps (tsnmap / tsnmapuv); (4) honour
`lvcol` (vertex colour) and `lum` where present. The same `mult` layer matters for truck materials too.
