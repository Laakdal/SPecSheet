Packed texture layout derived from our own bytes (license-safety re-derivation)
===============================================================================

Input: ETS2 1.60.1.7 archives base, base_vehicle, base_map, base_cfg, core,
base_share, def (opened read-only).

Command:
  cargo run --release -p specsheet-archive --example texture_layout -- \
    "<game>/base.scs" "<game>/base_vehicle.scs" "<game>/base_map.scs" \
    "<game>/base_cfg.scs" "<game>/core.scs" "<game>/base_share.scs" "<game>/def.scs"

Method (image record, 0x01):
- The image record's two u32 words are decoded with the bit layout in
  docs/formats/textures.md. width/height (dims word, 16 bits each, minus 1),
  mip count, DXGI format, face count and the two log2 alignments give a
  predicted size for the GDeflate-decompressed surface data.
- Four padding models are compared with the actual decompressed length, for
  up to 25 textures per (DXGI format, face count) bucket. In every model,
  padding goes BEFORE each mip (image alignment) and BEFORE each row (pitch
  alignment); the data ends with the last row, unpadded. Padding the last
  row too fails: 512x512 BC3 with 10 mips is 352,784 bytes, which ends 16
  bytes (one 4x4 block) after the last mip's 512-byte boundary.
- Only "pitch + image alignment" matches every texture of every format that
  pixel_layout knows, across 1x1-block tail mips, non-square sizes and
  6-face cube maps. So the bit fields are confirmed jointly: a wrong mip count,
  format, face count or alignment would break the exact size.
- Cube flag (bits 12-13): the tally over every texture in these archives is
  {(cube false, 1 face): 62,191, (cube true, 6 faces): 60}. The flag is set
  exactly on the six-face textures.
- Face-major order (all mips of face 0, then face 1) is not testable by size;
  it stays a Hypothesis (the DDS convention).
- DXGI 67 (R9G9B9E5_SHAREDEXP: skyboxes, HDR brightness UI images) and 75
  (BC2_UNORM_SRGB) appear. 67 is missing from pixel_layout, so those
  textures do not unpack (none is used by trucks).

Method (sample record, 0x02): tally per top-level directory, then look at
which textures carry the rare states. The meaning follows from the content:
- bits 0/1 clear (point sampling) only on lookup data: MLAA weights, jitter
  map, deferred attribute LUTs, window-interior LUTs, notfound;
- address value 3 (clamp to border) only on projected shadow and light masks;
- U = 0 (repeat) with V = 2 (clamp to edge) on skybox panoramas: they wrap
  horizontally and clamp vertically. So bits 4-6 are U, bits 7-9 are V,
  0 = repeat, 2 = clamp to edge.
- Values 1 and 4+ (clamp, mirror ...) never occur in these archives.
