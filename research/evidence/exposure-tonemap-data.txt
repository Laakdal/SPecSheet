Exposure, tonemap and reflection keys: executable tables and climate data
==========================================================================

Sources (ETS2 1.60.1.7, read-only):
- the executable's attribute tables (tools/research/attr_tables.py, keys
  eye_adaptation_speed, light_environment, camera_fov);
- /def/climate/<name>/{nice,bad}.sii (dumped with the scs example) and
  /def/desktop/config*.sii, /def/truck_config_scene.sii.
Hex floats in SII (&xxxxxxxx) are decoded as big-endian IEEE 754 from the hex text.

Observations:
- The world climates (default, reference, grayscale, underground) use a
  middle grey near 0.18, contrast ~0.1-0.39, shoulder ~0.54-1.34, and an
  adaptive exposure scale whose range reaches the hundreds to thousands. Their
  light values are tiny absolute numbers (e.g. sun ~4e-4, ambient ~3e-5 in
  reference), which the scale brings to display range.
- The `black` and `integrity` climates fix the exposure: min_scale =
  max_scale = 5.555 (= 1/0.18), scale_override 0, contrast 0.1, shoulder 1,
  target_gray 0.18. `black` also has no bloom (intensity 0). These look like
  profiles for non-world scenes. Which climate or exposure the tuning screen
  uses is Unknown.
- The tonemap operator itself lives in shader code (not read, D13). The key
  names (contrast, shoulder, a middle grey) suggest a filmic curve with those
  three controls (Hypothesis).

4. Engine reflection slots (static disassembly, tools/research/disasm.py)
- FUN_1411f20b0 (826 bytes) creates two engine-owned texture objects by
  resource name: "/material/environment/vehicle_reflection.tobj" and
  "/material/environment/generic_reflection.tobj".
- FUN_1403f51c0 (3,797 bytes) fills a table of four reflection slots
  (records of 0x48 bytes), each named by a path plus blur variants:
    slot 0 /material/environment/vehicle_reflection.tobj + _blurry3, _blurry4, _blurry5
    slot 1 /material/environment/generic_reflection.tobj
    slot 2 /material/environment/interior_reflection.tobj + _blurry2.._blurry5
    slot 3 /material/environment/building_reflection/building_ref.tobj
  (then dashboard, gps, bare_map and player_tag textures).
  Truck materials name these paths, including the interior_reflection_blurry2/3/4
  variants (research/evidence/material-survey.txt).
Observed: a material's texture_reflection that names one of these paths
resolves to an engine slot, not just to the file. Hypothesis: in a UI scene the
scene's vehicle_reflection cube fills slot 0, so it replaces the cube for every
material that names vehicle_reflection.tobj, while materials that name other
cubes (fuzzy_reflection, soft_reflection, ...) keep their own. The code that
loads the scene's vehicle_reflection (scene class +0x1d8) into the slot is not
located yet (Unknown).

5. How the CPU packs the post-processing uniforms (static disassembly)
- FUN_1413c9f90 registers each deferred uniform by name with its own callback
  (code address passed next to the name): deferred_param_histogram_params,
  eye_adapt_factors, low_intensity_factors, low_intensity_color,
  tonemap_params, bloom_params, dof_range, color_correction, among others.
  Callbacks: eye_adapt_factors 0x1413c9980, tonemap_params 0x1413c9c60,
  bloom_params 0x1413c9e40, color_correction 0x1413c8910.
- tonemap_params (0x1413c9c60): six vec4, copied unchanged from a runtime
  post-processing object R (reached through the render context, +0x18 then
  +0x50). Per index, the four floats come from these R offsets:
    T0 = (+0x1e8, +0x24c, +0x250, +0x1f4)
    T1 = (+0x204, +0x208, +0x20c, +0x210)
    T2 = (+0x214, +0x218, +0x21c, +0x220)
    T3 = (+0x224, +0x228, +0x22c, +0x230)
    T4 = (+0x234, +0x238, +0x23c, +0x240)
    T5 = (+0x244, +0x248, +0x1fc, +0x200)
  No arithmetic happens here: the curve's coefficients are computed earlier
  into R.
- eye_adapt_factors (0x1413c9980): two vec4 are computed, the rest are zero.
    E0 = (L(max(R+0x1d4, 1e-10)), L(max(R+0x1d8, 1e-10)), R+0x1dc, R+0x1dc)
    E1 = (sat(1 - R+0x1e0)^(R+0x264), sat(1 - R+0x1e4)^(R+0x264), 0, 0)
  where sat clamps to [0, 1] and L is a logarithm: a C-runtime routine
  reached through a stub (0x141c91ae4), base not settled. Without R, all
  factors are zero.
  Reading (Hypothesis): E0 = log min/max exposure scale, E1 = per-frame
  adaptation from the dark/bright speeds with a time-step exponent.
- Not established: which code fills R from the sun_profile keys (many
  functions touch the same offsets; candidates 0x14045dd90, 0x140ba27e0,
  0x140ae2460); the bloom and colour-correction callbacks; which climate or
  sun profile the tuning screen uses; where a scene's pre_exposure (scene
  class +0x44) enters (it is in none of these callbacks).

6. bloom_params, color_correction and the scenes' pre_exposure (static)
- bloom_params callback (0x1413c9e40, a leaf function without .pdata): one
  vec3 copied unchanged from R+0x254, +0x258, +0x25c.
- color_correction callback (0x1413c8910): one vec4 copied unchanged from
  R+0xd8..+0xe4; without R it writes nothing.
- How a UI scene config is applied (FUN_140f8a590, which also logs
  "Enforcing 'floor_reflection: false' ..."): it copies light_ambient,
  light_diffuse, light_specular and light_environment into the scene state,
  and normalises light_direction. Then:
    pre_exposure = the scene's pre_exposure, when > 0;
    otherwise 0.0348717 * (ambient.r + ambient.g + ambient.b
                            + 0.525322 * (diffuse.r + diffuse.g + diffuse.b)).
  /def/truck_config_scene.sii (ambient 0.3 each, diffuse 1.2 each, no
  pre_exposure): 0.0348717 * (0.9 + 0.525322 * 3.6) = 0.0973.
- FUN_140f89490(state, k) writes the scene state into a global lighting block
  (pointer at 0x1434e8258):
    +0x18 ambient*k, +0x24 diffuse*k, +0x30 specular*k, +0x3c 1.0, +0x40 1.0,
    +0x44 0, +0x48 pre_exposure*k, +0x4c light_environment*k, +0x50 k,
    then the light direction.
  The UI scene setup calls it with k = 1.0 (0x140f8adf4); a second caller
  passes k as an argument (Hypothesis: a fade).
- The world lighting update (FUN_1404dca40, sun angles and climate values)
  writes the same block with +0x48 = 1.0 (constant) and +0x3c/+0x40/+0x44/
  +0x4c/+0x50 from the climate state.
Observed: +0x48 is a pre-exposure multiplier. The world sets 1.0; a UI scene
sets its pre_exposure, derived from its lights when absent (0.0973 for the
tuning screen).
Not established: which of the 13 readers of +0x48 apply it and how (as
radiance x pre_exposure, or into the exposure/tonemap); whether the UI path
runs eye adaptation, and which values R holds in a UI scene. The UI path
reads no sun_profile in the functions seen.

7. The global lighting block is eutpp_scene_light (attribute table)
attr_tables.py on "limited_pre_exposure" gives class ptr 0x141d1ca40
(eutpp_scene_light) with these offsets, which equal the fields that
FUN_140f89490 (UI scene) and FUN_1404dca40 (world) write:
  +0x18 ambient, +0x24 diffuse, +0x30 specular (float3)
  +0x3c diffspec_conditional_mult   UI 1.0
  +0x40 light_source_visibility     UI 1.0
  +0x44 ec_adjustment               UI 0      (exposure-compensation adjustment)
  +0x48 limited_pre_exposure        UI pre_exposure (0.0973 for the tuning
                                    screen); world 1.0
  +0x4c environment                 UI light_environment
  +0x50 environment_conditional_mult  UI 1.0 (k)
  +0x54 aurora_diffuse
No CPU code reads +0x48 back through the global pointer (scan of every load
of 0x1434e8258 followed by a read of +0x48/+0x4c/+0x50: only one read, of
+0x4c, at 0x14050d21a). So the block is consumed as a whole: Hypothesis,
uploaded as shader constants. How limited_pre_exposure and ec_adjustment
enter the lighting or tonemap is therefore shader code (D13 spec scope).
Debug strings in the executable describe automatic exposure from the scene
histogram, with an option to "use only sun light value for exposure", and an
"Exposure compensation" setting.

8. Light-colour uniforms and two non-answers (static + one Ghidra run)
- FUN_1413c9f90 also registers the light uniforms, among them
  def_light_diffuse (cb 0x1413caf80), def_light_specular (0x1413caf10),
  def_light_ambient_environment (0x1413caff0),
  deferred_param_additional_ambient_color (0x1413c7eb0) and
  def_light_ambient_light_directional_effect_strength (0x1413cb3c0).
- def_light_diffuse and def_light_ambient_environment copy raw values from a
  light object L (render context +0x18, then +0x58; skipped when its flag
  word lacks 0x800 or L is not live):
    def_light_diffuse = L+0x70..0x78 (vec3);
    def_light_ambient_environment = L+0x60..0x6c (vec4: ambient rgb +
    environment in w, matching the spec's ambient.w).
  So whatever scales the light colours (limited_pre_exposure among others,
  per the spec) does it when L is filled, not in the callbacks.
- No function that loads the eutpp_scene_light pointer (0x1434e8258) also
  writes L's colour offsets: the hand-over goes through a copy or a
  virtual call (Unknown).
- Ghidra on 0x14045dd90 (ev_8c2b1139b62f6a16669810a446f40f15951d4c214169fa1e1c8120abc1923b8a):
  a constructor that zeroes a render object (including +0x1d4..+0x24c), with
  seven callers. It is not the tonemap filler; offset matching alone misled
  the static triage. 0x14086f430, which block-copies into the same offsets,
  computes bounds with sin/cos (shadow or culling setup), so it is not the
  filler either.
Still open: which code fills L and R from eutpp_scene_light and sun_profile,
i.e. whether limited_pre_exposure multiplies the light colours or the exposure.

9. Engine-filled material uniforms: the callbacks (static, 2026-10-29)
Method (read-only, no Ghidra): tools/research-style scripts in the session scratchpad
(string xrefs by RIP-relative LEA/MOV, capstone disassembly of .pdata extents, and a
linear disassembly to `ret` for leaf functions). Listings stay out of the repository.
- FUN_1403dcf80 registers the material uniforms: for each name it passes a callback
  (lea rdx) that fills that uniform. Callbacks used below:
    texture_reflection_modulator 0x1403d88c0   envmap_matrix 0x1403db190
    material1_data 0x1403db120 (both via the builder 0x1403daeb0)
    fwd_lights_data 0x1403d9460   material_luminosity 0x1403d8bf0 (scalar 0x1403d8a80)
    lamp_color_array 0x1403d8d00 -> 0x1403de230   lamp_contrast 0x1403d8d10
    luminosity_color_array 0x1403d8cf0 -> 0x1403de0c0   es_world_up 0x1403d9d60
  The other ~120 registered names and callbacks are in the scratchpad (callbacks.txt).
- The light object every callback reads is ctx+0x18 -> +0x68 (present when the context
  flag 0x2000 is set). Its offsets are those of eutpp_scene_light (section 7):
  +0x18 ambient, +0x24 diffuse, +0x30 specular, +0x3c diffspec_conditional_mult,
  +0x44 (named ec_adjustment in the table), +0x48 limited_pre_exposure,
  +0x4c environment, +0x50 environment_conditional_mult.
- fwd_lights_data (4 vec4):
    [0] = (ambient.rgb, environment)
    [1] = light direction (from a direction table indexed by a 13-bit id at +0x62)
    [2] = diffuse.rgb * diffspec_conditional_mult
    [3] = specular.rgb * diffspec_conditional_mult
  limited_pre_exposure is not read: the forward sun and ambient colours are not scaled
  by pre-exposure.
- texture_reflection_modulator (one float), in order:
    the material binds no texture in its "texture_reflection" slot -> 9999.0;
    its reflection texture is in an engine set at ctx+0x48 -> 1.0;
    otherwise (and when ctx+0x48 is null) -> environment_conditional_mult (+0x50).
  The UI scene writes +0x50 = k = 1.0 (section 6), so it is 1.0 on the tuning screen.
- lamp_contrast = 1 + 3 * (+0x44). The UI scene writes +0x44 = 0, so it is 1.0 there.
- lamp_color_array / luminosity_color_array: copied from an array on the drawn object
  (ctx+0x18 -> +0x98 for lamps, +0xa0 for backlights; count at +0x28, data at +0x20),
  each rgb multiplied by limited_pre_exposure (+0x48; 1.0 without a light object), alpha
  unchanged. Entries past the object's count are written as zero.
- material_luminosity = (o+0x18, o+0x1c, o+0x20, s * o+0x24), o = ctx+0x18 -> +0x90
  (context flag 0x40000; an engine object, contents not decoded), with the scalar s from
  0x1403d8a80:
    (x, y) = the material's luminance pair (attribute slot 15; luminance_output and
    luminance_night by order, Hypothesis); x = 0 -> 50; y = 0 -> x;
    t = 0, or 1 when forced by the caller or an effect flag (bit 21), or +0x44 of the
    light object, unless effect flag bit 20 keeps it 0;
    v = x when x == y; otherwise exp(lerp(ln x, ln y, t)) when x > 0, else lerp(x, y, t);
    s = v * limited_pre_exposure * 0.001 when x > 0;  s = |v| when x <= 0.
  So luminance_output -1 gives s = 1 (no pre-exposure), and 0 means 50 nits.
- material1_data (6 vec4; envmap_matrix is its first four):
    rows 0, 1, 3 = the camera object's +0x58, +0x68, +0x88 (ctx+0x18 -> +0, flag bit 0);
    row 2 = minus the camera object's +0x78 (all four components negated);
    [4].rgb = material colour slot "color2" * slot "specular" (two 3-vectors), unless the
      effect flag bit 9 (0x200) is set, then slot "color2" alone;
    [5] = (0, 0, f0, f1):
      effect flags & 0x18000 == 0: (f0, f1) = the material's fresnel pair, raw;
      0x8000: f0 = 0.14; 0x10000: f0 = 0.035; 0x18000: f0 = 0.07; f1 = 1;
      in those three modes, a fresnel pair whose second value is -1 gives
      f0 = clamp(first value, 0, 1) instead.
  The slot names come from the engine's material-slot table (0x1425e966c, 32-byte
  entries: default vec4, then a name pointer): slot 4 = fresnel, default (0.2, 0.9),
  which fixes the slot numbering; slot 1 = specular, slot 9 = color2, slot 15 = aux5.
  Effect flags are the .rfx "flags:" field: eut2.glass 0x18000, eut2.truckpaint
  0x10100 (and 0x10000 with flipflake), dif.spec/lamp/dif.lum/unlit 0 (no field).
- The .mat float3 inputs diffuse, specular and env_factor (and their _secondary forms)
  are clamped to [0, 5] per component when applied (FUN_14031c230); glass_tint_color,
  the paint and showroom colours are not.
