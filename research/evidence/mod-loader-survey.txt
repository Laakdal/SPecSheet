Mod loader survey (finding F14, docs/formats/mods.md)
=====================================================

Sources (all read-only):
  - The user's mod folder: <home>\mod (55 files; the home dir is relocated
    with -homedir, so this is "/home/mod" to the game).
  - Steam Workshop content: <steam>\steamapps\workshop\content\227300 (77 items).
  - The game's own log: <home>\game.log.txt, one session of ETS2 1.60
    (paths in the log name another drive letter; same install).
  - String inventory of bin\win_x64\eurotrucks2.exe (1.60.1.7, sha256
    b7dffe6b27402c7db6dfd52cf982cd5bf292584138b35e3eb8efb311814ab3f8), grep of
    printable runs; nothing was executed.
  - Our probe: cargo run --release -p specsheet-archive --example mod_probe -- <mod dir>
  - Python zipfile/zlib (stdlib) over the ZIP packages, read-only.
Mod contents (third-party data) are not reproduced; only attribute names,
version-gating values, counts and header bytes are quoted.


1. Container is chosen by content, not by extension
---------------------------------------------------
First 4 bytes of each file in /home/mod, against the driver the game logged
for it at start-up ("[hashfs] X: Created" or "[zipfs] X: Created"):

  magic        files   driver in log   extensions seen
  SCS# v1        20    [hashfs]        .scs
  SCS# v2         2    [hashfs]        .scs
  PK\3\4         33    [zipfs]         .scs (28) and .zip (5)

Every file matched: no PK file was logged as hashfs, no SCS# file as zipfs.
So a ".scs" mod is very often a plain ZIP.


2. HashFS v1 (our observations, mod_probe)
------------------------------------------
Header, first 0x14 bytes, e.g.
  PNG_PE_BASE_1.scs        53 43 53 23 01 00 00 00 43 49 54 59 96 08 00 00 00 10 00 00
  Add-On MAN TG3 ... .scs  53 43 53 23 01 00 14 49 43 49 54 59 86 1d 00 00 c0 0f 6d 52
  = magic "SCS#", u16 version 1, u16 salt, "CITY", u32 entry count,
    u32 entry-table offset. Entry counts equal the counts the game logged
    (2198, 7558, 56403, ...) for all 20 files.
  19 files: salt 0, table at 0x1000. One file: salt 0x4914, table at the end
  of the file (0x526d0fc0 in a 1,383,121,024-byte file).

Entry table: count x 32-byte records, sorted ascending by hash in all 20:
  +0 u64 hash, +8 u64 offset, +16 u32 flags, +20 u32 crc (not checked),
  +24 u32 size, +28 u32 stored size.
  No record points past the end of its file.

Flags per producer:
  flags {0,1}   (PNG packs)         stored == size for every entry
  flags {0,2,3} (Gloover pack)      every flag-2/3 entry has stored != size and
                                    inflates with zlib to exactly `size`
  flags {4,5}   (ProMods packs)     stored == size for every entry
  -> bit 0 = directory (its content is a listing, in all three producers),
     bit 1 = zlib-compressed, bit 2 unknown (set on every ProMods entry).

Directory listing: text, one name per line, sub-directories prefixed "*".
  Line ends are "\n" (PNG, ProMods) or "\r\n" with a trailing empty line
  (Gloover). Example: "*flare\r\n\r\n".

Path key: CityHash64 (our city_hash_64, v1.0.3) of the path without a leading
slash, as in v2. With a non-zero salt, the key is the hash of the salt's
decimal text followed by the path ("18708manifest.sii" for salt 0x4914).
  "manifest.sii" resolves in 20/20 files with this rule; no other candidate
  form (salt as 2 raw bytes, leading "/") resolves.
  The root directory ("" key) is absent in all 20 files, so v1 mods cannot be
  listed from the root; files are reachable only by known path. Directory
  entries further down do exist.
  manifest.sii is plain SII in all 20 and gives the same attribute set as the
  ZIP manifests (section 4).

4. ZIP packages
---------------
  33 ZIP files. Compression methods in the central directory: only 0 (stored)
  and 8 (deflate). No ZIP64 (all offsets and sizes < 4 GiB).
  32 open with Python zipfile. One (Project_Ultimate_Weather_2.0.scs) is
  deliberately malformed:
    - central directory: general-purpose flag bit 0 (encrypted) on all 11
      entries, method 8, CRCs that match nothing;
    - local headers: flag 0, method 1, a different CRC that also matches
      nothing; the sizes match the central directory;
    - the data after each local header (30 + name + extra) is plain raw
      deflate and inflates to exactly the central-directory size.
    The game logged it "Created, 11 entries" with no zipfs error, so the game
    ignores the encryption bit and CRCs (Hypothesis: it takes the method from
    the central directory and does not verify CRC).
  Layout of a package root:
    - ordinary: manifest.sii, icon (.jpg), description (.txt), then def/,
      vehicle/, material/, model/, ...;
    - multi-folder (3 files): manifest.sii and icon at the root, plus base/ and
      dlc_<name>/ folders holding the content.
  One package (No_Driver.scs) has no manifest.sii; the log says:
    "[mod] Mod package 'No_Driver' does not contain a manifest file
     'manifest.sii', creating default information set."

manifest.sii (unit "mod_package : <name>") attribute names seen across the
ZIP, v1 and v2 manifests:
  package_version, display_name, author, category[], icon, description_file,
  compatible_versions[], dlc_dependencies[], mp_mod_optional
  Log warnings that match missing or invalid fields:
    "No display_name defined in X. Using package name instead."
    "No valid categories defined for X. Setting defaults."
    "Unknown category '' defined for X. Ignoring."


5. Version gating explains both "Incompatible mod" warnings
-----------------------------------------------------------
  "[mods] Incompatible mod - Add-On MAN TG3 2020 by Gloover"
      manifest compatible_versions: "1.57.*", "1.58.*", "1.59.*"
  "[mods] Incompatible mod - Project_Ultimate_Weather_2.0"
      manifest compatible_versions: "1.58.*", "1.59.*"
  The game is 1.60.1.7. Checked in both directions over all 54 manifests
  (fnmatch of "1.60.1.7" against each compatible_versions glob; no array =
  compatible): exactly these two do not match, and these two are exactly the
  mods the log calls incompatible.
    without compatible_versions: 24 ZIP manifests
    with a 1.60.* glob: 7 ZIP (Sanax DEF lists 1.58-1.60, the rest 1.60),
      19 v1 (PNG 1.58-1.60, ProMods 1.60)
    without a 1.60 glob: Gloover MAN (v1), Project_Ultimate_Weather (ZIP)

  The active list starts with the ProMods packages and ends with

  the profile (profile.sii, which is ScsC-encrypted here; not read).

Multi-folder packages at profile load (Sanax_volvo_fh_2022_p_DEF.scs):
  start-up scan requested 18 sub-directories: base + 17 dlc_* folders;
  profile load mounted 16 devices for the same file: base + 15 dlc_* folders.
  The two skipped are dlc_schoch and dlc_xmas, the only two whose names match
  no installed DLC (installed: dlc_hs_schoch, dlc_christmas).
  -> base/ is always mounted; dlc_<name>/ is mounted only when that DLC is
     installed (Confirmed for this case; ownership vs. installation not
     separated, since every installed DLC is owned here).


7. Workshop items
-----------------
  Every one of the 77 item folders has versions.sii. Units are
  "package_version_info : .<name>" with package_name and optional
  compatible_versions[]. Typical names: .latest, .universal, .<NNN>_content.
  The package a unit names is a sub-folder (mounted as a directory device,
  e.g. ".../2487007069/universal mounted to mod pool.") or a .zip/.scs file
  in the item folder (".../3732555345/universal.scs mounted to mod pool.").
  Item folder contents across all 77 items, digits replaced by N:
    77 versions.sii, 39 N_content, 30 universal, 16 N, 15 universal.zip,
    11 N_content.zip, 3 universal.scs, 3 latest.zip, ...
  In the log, Workshop packages are named mod_workshop_package.<16 hex digits>
  (the published file id in hex: 0x00000000CE19853F = 3457779007).
