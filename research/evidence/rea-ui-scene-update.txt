What the function does, in order
1. Virtual calls on the scene and the render view that set up the view (not decoded).
2. Sets a byte of the render view (+0x25b) to 1, and a flag word (+0x2a0) to 0xd01b when a
   scene flag (+0x331) is set, else 0.
3. In one scene mode (+0x250 == 1), builds and applies a camera setup (helper 0x140f8d8e0).
4. Writes the scene light block (FUN_140f89490, k = 1.0; section 6/9 of
   exposure-tonemap-data.txt).
5. Takes the light direction from the block's direction table (id at block +0x62), turns it
   into a world position (x4096, split into 512 m sectors), and calls 0x1403d6b20 with that
   position, weight 1.0 and the luminance 0.3 R + 0.59 G + 0.11 B of the block's SPECULAR
   colour (+0x30). Static read of 0x1403d6b20: with weight >= 1 it takes the new position at
   once and stores a strength sat(500 * luminance). Hypothesis: the sun-visibility/flare
   source; with light_specular (1.2,1.2,1.2) the strength is 1.
6. Copies the scene unit's truck_steering_rot (+0xdc of the ui_truck_scene_config class) into
   two render-view fields (+0x1408, +0x640) and zeroes +0x1410.
7. Further view and scene updates through virtual calls; marks a scene object's state 2.

Answer to the open question
- Confirmed: the UI scene update writes no exposure, adaptation or tonemap parameter. Its only
  lighting output is the scene light block and the sun-visibility source above.
- So the eye-adaptation limits and speeds the deferred pipeline uses on the tuning screen (the
  render-parameter object R, +0x1d8..+0x1e4, read by the eye-adapt uniform callback 0x1413c9980)
  are not set by the UI scene. Hypothesis: R keeps its default construction or the last
  climate state. Unknown: those values.

Side finding (game data, Confirmed by reading the files)
- ui_truck_scene_config has a key vehicle_lights_on (+0x21e). 8 of the 10 /def/desktop scene
  configs set it true (config, christmasbg, halloween_2023, hangar, night_city, northlights,
  under_bridge, xmas); dark_studio and waves do not set it. /def/truck_config_scene.sii does
  not set it. Which lights it switches on is not read.

Where vehicle_lights_on goes (static, tools/research/{xref,attr_tables,disasm}.py)
- No code references the key's string; the attribute table maps it to the scene unit's +0x21e.
- The only function that reads +0x21c, +0x21d and +0x21e together, 0x140f88110 (scene apply),
  copies +0x21e into the UI scene object's +0x331.
- FUN_140f8acc0 (above, step 2) turns that byte into the render view's light mask (+0x2a0):
  0xd01b when set, 0 otherwise. Confirmed.
- What the mask's bits mean is Unknown. One name-to-number table of vehicle light types
  (0x142c3c598: front_left_turn_signal 0, rear_left_turn_signal 1, reverse 2, high_beam 3,
  front_right_turn_signal 4, daytime_running 5, front_positional 6, none 7, rear_positional 8,
  rear_right_turn_signal 10, brake 11, low_beam 12) does not explain it: read with it, 0xd01b
  would switch on three of the four turn signals and no positional lights, and bits 14 and 15
  have no name there. So the mask uses another numbering.
